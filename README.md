# Portfolio Display

작가가 직접 자기 포트폴리오 사이트를 운영할 수 있게 만든 웹 애플리케이션입니다.

작품을 올리고 순서를 바꾸는 것은 물론, 사이트의 색상과 폰트, 메인 화면 문구까지
관리자 페이지에서 바꿀 수 있습니다. **글 하나를 고치려고 개발자를 부를 일이 없도록**
만드는 것이 목표였습니다.

운영 중인 사이트: https://jaehoonjeong.com

---

## 왜 만들었나

작가에게 필요한 것은 CMS의 모든 기능이 아니라, 작품을 보여주는 몇 가지였습니다.

- 이미지가 잘리지 않고 원본 비율 그대로 보일 것
- 작품 순서를 직접 정할 수 있을 것
- 사이트 분위기(색, 폰트)를 코드 수정 없이 바꿀 수 있을 것
- 마음에 드는 작품 링크를 그대로 공유할 수 있을 것

워드프레스처럼 큰 도구를 쓰면 이 네 가지를 위해 훨씬 많은 것을 관리해야 합니다.
그래서 필요한 만큼만 직접 만들었습니다.

## 화면

**공개 사이트** (`/`)

왼쪽 사이드바에 카테고리, 오른쪽에 작품이 나열됩니다. 작품을 누르면 상세 팝업이
열리고, 여러 이미지와 YouTube 영상을 한 화면에서 전환할 수 있습니다.

주소는 `/artwork/12` 형태입니다. 새로고침해도 보던 작품이 그대로 열리고,
링크를 공유하면 메신저 미리보기에 그 작품의 제목과 이미지가 나옵니다.

**관리자 페이지** (`/admin`)

카테고리, 게시글, 사이트 설정, 계정을 관리합니다. 설정 화면에는 실시간 미리보기가
있어서 색을 바꿀 때마다 사이트에 들어가 확인할 필요가 없습니다.

| 구분 | 사용 기술 |
| --- | --- |
| 백엔드 | Java 11, Spring Boot 2.7 (Web, Data JPA, Security, Validation) |
| 데이터베이스 | MariaDB |
| 프론트엔드 | HTML / CSS / 순수 자바스크립트 |
| 외부 라이브러리 | Quill.js (리치 텍스트), PDF.js (CV 렌더링) |
| 테스트 | JUnit 5, Mockito, Spring Security Test, H2 |

프론트엔드에 프레임워크를 쓰지 않은 것은 의도적인 선택입니다. 화면이 여섯 개
남짓이고 상태도 단순해서, 빌드 도구를 들이는 비용이 얻는 것보다 컸습니다.

## 기능

**콘텐츠 관리**

- 카테고리 CRUD. 타입은 `PHOTO` / `ARTICLE` / `HTML` 세 가지
- 게시글 CRUD. 이미지 여러 장, YouTube 영상, 항목별 설명과 표시 위치 지정
- 게시글과 카테고리의 표시 순서를 화면에서 직접 변경
- CV 카테고리는 PDF를 올리면 페이지 안에서 바로 렌더링

**사이트 설정**

- 사이트 제목, 메인 화면 소개 문구, 최근 작품 노출 여부
- 배경 색상과 이미지, 텍스트와 사이드바 색상
- 웹폰트 (Google Fonts 프리셋 제공, 직접 입력도 가능)
- 로고, 파비콘, 연락처, 소셜 링크, 푸터 문구

**링크 공유와 검색 노출**

- 작품마다 고유한 주소 (`/artwork/12`)
- 서버가 그 작품의 제목 · 설명 · 대표 이미지를 첫 응답의 메타 태그에 넣어 줌
- `sitemap.xml`, `robots.txt` 자동 생성

**파일 업로드**

- 확장자와 MIME 타입 이중 검증, 최대 10MB, UUID 파일명으로 저장
- 업로드 시 목록용 축소본을 자동 생성 (최대 900px, EXIF 회전 반영)
- 경로 탈출 차단

**계정**

- 관리자 계정은 DB에 BCrypt 해시로 저장
- 관리자 페이지에서 아이디와 비밀번호 변경
- 비밀번호 분실 시 환경 변수로 초기화

## 만들면서 했던 선택들

**이미지를 자르지 않기로 한 것**

처음에는 목록을 16:10으로 고정해 격자를 깔끔하게 맞췄습니다. 그런데 세로로 긴
회화가 위아래로 잘려 나갔습니다. 작가의 사이트에서 작품이 잘리는 것은 격자가
흐트러지는 것보다 나쁜 문제라고 판단해서, 원본 비율을 그대로 보여주는 쪽으로
바꿨습니다.

**축소본을 서버에서 만드는 것**

목록에 원본(최대 10MB)을 그대로 쓰면 첫 화면이 느립니다. 업로드 시점에 900px
축소본을 만들어 두고 목록에서는 그것만 씁니다. 축소본이 없으면 화면이 자동으로
원본으로 되돌아가므로, 이전에 올린 파일도 문제없이 보입니다.

**한 칼럼에 두 가지 의미를 담지 않기**

처음에는 `description` 하나에 PHOTO 의 평문 설명과 ARTICLE 의 Quill 델타 JSON 을
같이 담았습니다. 읽는 쪽이 매번 파싱을 시도해 보고 실패하면 평문으로 취급해야 했습니다.
`PostImage.imageUrl` 도 종류에 따라 파일명이거나 YouTube 주소였습니다.

지금은 용도별로 칼럼을 나눴습니다. 덕분에 "이 항목이 가리키는 업로드 파일"을 묻는
코드가 종류를 따져 묻지 않고 한 줄로 끝납니다. 콘텐츠 종류도 문자열 대신 enum 이라
오타가 컴파일 단계에서 걸립니다.

기존 데이터는 `LegacyDataMigration` 이 시작할 때 옮깁니다. 이미 옮긴 행은 건드리지
않으므로 여러 번 실행해도 안전합니다. 스키마 변경이 더 늘어나면 Flyway 같은 도구로
옮기는 편이 낫습니다.

**게시글 수정 시 파일 삭제 조건**

처음에는 "썸네일이 바뀌면 이전 파일 삭제"였습니다. 그런데 이미지 순서를 바꾸면
첫 번째 이미지가 썸네일이 되면서, 여전히 쓰이고 있는 파일이 디스크에서 지워졌습니다.
지금은 새 요청에서 더 이상 참조되지 않는 파일만 지웁니다.

**해시 라우팅을 걷어낸 것**

처음에는 주소에 `#/artwork/12` 를 썼습니다. 정적 파일 하나로 돌아가는 구조를
유지하면서 새로고침과 뒤로가기를 얻는 가장 싼 방법이었습니다.

문제는 해시가 **서버로 전송되지 않는다**는 점이었습니다. 어떤 작품을 공유해도
서버는 똑같은 요청을 받으니 똑같은 메타 태그만 내려줄 수 있고, 메신저 미리보기에는
늘 사이트 대표 문구만 떴습니다. 검색 엔진도 작품을 개별 페이지로 보지 않습니다.
작가의 사이트에서 "이 작품 봐봐" 하고 링크를 보내는 것이 가장 흔한 사용 방식인데,
그게 제일 안 되고 있었습니다.

지금은 실제 경로(`/artwork/12`)를 쓰고, 서버가 그 주소를 보고 작품의 제목 ·
설명 · 대표 이미지를 첫 HTML 의 `<head>` 에 심어 줍니다. 화면을 그리는 일은
여전히 전부 자바스크립트가 하고, 서버가 하는 일은 메타 태그 구간 하나를
바꿔 끼우는 것뿐입니다 — 템플릿 엔진을 들이지 않았습니다.

이미 공유된 예전 주소를 위해, `#/artwork/12` 로 들어오면 새 주소로 넘겨줍니다.

## 로컬에서 실행하기

MariaDB와 JDK 11 이상이 필요합니다.

```bash
# 1. 데이터베이스 생성
mysql -u root -p -e "CREATE DATABASE portfolio_dev"

# 2. 접속 정보 수정
#    src/main/resources/application-local.properties 의
#    spring.datasource.username / password 를 본인 환경에 맞게

# 3. 실행
mvn spring-boot:run
```

- 공개 사이트: http://localhost:8081
- 관리자 페이지: http://localhost:8081/admin

첫 실행 시 `admin.username` / `admin.password` 설정값으로 관리자 계정이 만들어집니다.
로그인 후 **계정 · 비밀번호** 메뉴에서 바로 변경하세요.

## 환경 변수

운영 환경에서는 다음을 반드시 설정해야 합니다. 값이 없으면 애플리케이션이 뜨지 않습니다.

| 변수 | 설명 |
| --- | --- |
| `DB_PASSWORD` | 데이터베이스 비밀번호 |
| `ADMIN_USERNAME` | 관리자 계정 초기 아이디 |
| `ADMIN_PASSWORD` | 관리자 계정 초기 비밀번호 |
| `ADMIN_RESET_PASSWORD` | `true` 로 한 번 재시작하면 위 값으로 계정 초기화 (평소 `false`) |
| `CORS_ALLOWED_ORIGINS` | 허용할 도메인 (쉼표로 구분). 같은 도메인에서만 쓰면 비워 둡니다 |
| `SITE_BASE_URL` | 공유용 메타 태그에 쓸 절대 주소. 보통은 비워 두면 요청에서 알아냅니다 |

관리자 계정은 최초 실행 시 위 값으로 만들어지고, 이후에는 관리자 페이지에서 변경한
값이 DB에 저장됩니다.

## 보안

- **인증** 폼 로그인(세션) 과 HTTP Basic(스크립트용) 두 경로를 지원합니다.
  비밀번호는 BCrypt 해시로만 저장합니다.
- **CSRF** 쓰기 요청에 토큰을 요구합니다. 화면이 정적 HTML 이라 토큰을 쿠키로 내려주고
  자바스크립트가 `X-XSRF-TOKEN` 헤더에 실어 보냅니다.
- **로그인 시도 제한** IP 와 아이디를 각각 세어 5회 연속 실패하면 15분간 잠급니다.
  성공하면 카운터를 초기화합니다.
- **세션 쿠키** `HttpOnly`, `SameSite=Lax` 를 적용하고, 운영에서는 `Secure` 를 켭니다.
- **업로드** 확장자와 MIME 타입을 함께 검사하고, 저장 경로 밖으로 나가는 요청을 막습니다.
  업로드 파일을 리버스 프록시가 직접 내보내는 구성이라면, 그 경로에도 CSP 를 붙여
  SVG 안의 스크립트가 실행되지 않게 해야 합니다.

> 운영 프로파일(`prod`)은 세션 쿠키에 `Secure` 를 붙이므로 **HTTPS 가 필요합니다.**
> 평문 HTTP 로 접속하면 로그인 상태가 유지되지 않습니다.

## 테스트

```bash
mvn test
```

실제로 버그가 났던 지점과 보안 규칙을 덮었습니다.

| 대상 | 무엇을 검증하나 |
| --- | --- |
| `PostServiceTest` | 게시글 수정 시 아직 쓰이는 파일을 지우지 않는지 |
| `SeoServiceTest` | 메타 태그 내용과 이스케이프, 사이트맵 |
| `PublicPageControllerTest` | 작품 주소가 그 작품의 메타 태그를 내려주는지 |
| `LegacyDataMigrationTest` | 예전 구조의 데이터를 옮기고, 여러 번 돌려도 같은지 |
| `LoginAttemptServiceTest` | 로그인 잠금과 해제, 성공 시 초기화 |
| `FileStorageServiceTest` | 축소본 생성, 확장자·MIME 검증, 경로 탈출 차단 |
| `AdminAccountServiceTest` | 비밀번호 변경 규칙과 계정 초기화 |
| `SecurityRulesTest` | 공개 조회 허용, 쓰기 인증, CSRF 강제 |

시간에 따라 동작이 달라지는 코드는 `Clock` 을 주입받습니다.
"15분 뒤 잠김이 풀린다"를 검증하려고 15분을 기다리지 않기 위해서입니다.

## 알려진 한계

정직하게 적어 둡니다. 개인 포트폴리오 사이트라는 사용 환경을 전제로 한 선택들입니다.

- 관리자 계정은 하나입니다. 여러 명이 함께 쓰는 상황은 고려하지 않았습니다.
- 로그인 시도 기록을 메모리에 둡니다. 서버를 재시작하면 초기화됩니다.
  서버가 한 대이고 계정이 하나라 별도 저장소를 두지 않았습니다.
- 화면 동작을 자동으로 검증하지는 않습니다. 서버 로직과 보안 규칙은 테스트로 덮었지만,
  화면은 실제 브라우저로 확인하는 방식입니다.
